# S03 — Apply as an organizer and receive an administrator decision

Status: specification of the S03 design confirmed on 2026-10-23. The user also confirmed the public HTTP and browser testing boundaries during specification preparation. Implementation is a separate task.

Issue: https://github.com/AxIon-200/aventix-development/issues/126

## Problem Statement

A person who wants to organize music events cannot submit a real organizer application. The application screen is a disabled preview, administrator review uses sample data, and the existing account system does not enforce organization approval. Applicants cannot receive a reliable administrator decision, and administrators cannot preserve reasons, resolve competing decisions, or withdraw organizer access safely.

Aventix requires a separate organizer account with its own normalized email address. Applicants must verify that address before review, and only approved organizers may log in. People need truthful outcomes when submission or email delivery fails; administrators need durable records that explain what was reviewed, who decided, and which decision is currently effective.

## Solution

Enable application submission that creates a separate organizer account and organization profile together, records current-terms consent, and requests email verification. Administrators review verified applications, approve or reject them with permanent decision history, and communicate the result by email. Rejection is final for that account. Approved organizers can log in with their original password; pending and rejected applicants receive status explanations only after supplying correct credentials and never receive a session.

Provide live administrator search, pagination, status counts, application details, recent owned events, CSV export, and decision-email retry controls. Include organization suspension and reinstatement, with immediate session invalidation on suspension and fresh login after reinstatement. Preserve existing events, sales, tickets, and attendee access when an organization is suspended. Keep email verification, organization approval, organization suspension, and account disabling distinct.

## User Stories

1. As a prospective organizer, I want to submit a real application from the organizer registration screen, so that an administrator can consider my organization.
2. As a person who already has an attendee account, I want to apply using a separate organizer account and email address, so that my attendee identity remains unchanged.
3. As an applicant, I want one dedicated organizer account to represent one organization, so that responsibility for its application and events is clear.
4. As an applicant, I want to supply my first name, last name, email, and password, so that my organizer identity has its own credentials and contact details.
5. As an applicant, I want to provide an optional phone number, so that I can add contact information without making it a prerequisite.
6. As an applicant, I want to supply an organization name and describe the music events it intends to run, so that the administrator has useful information for review.
7. As an applicant, I want field requirements and length limits explained, so that I can correct invalid input before resubmitting it.
8. As an applicant, I want organization names to permit duplicates, so that another organization's name does not incorrectly prevent my application.
9. As an applicant, I want to read and accept the current terms, so that my consent is informed and recorded against the correct version.
10. As an applicant, I want an outdated terms version or unavailable terms configuration handled through the existing account flow, so that the service does not fabricate consent.
11. As an applicant, I want my account and application saved together, so that a partial failure cannot leave me with an unusable identity or orphaned application.
12. As an existing account holder, I want duplicate normalized-email submissions rejected without changing my credentials or details, so that another submission cannot replace my identity.
13. As an applicant, I want submission to create no session, so that registration is distinct from approval and login.
14. As an applicant, I want a verification email using the existing verification flow, so that I can prove ownership of my email address before review.
15. As an applicant, I want email verification to preserve pending organization approval, so that verifying my address is never mistaken for permission to organize events.
16. As an applicant whose verification email fails, I want to know that my application was saved and how to request another email, so that I do not create duplicate submissions.
17. As an applicant whose submission response is lost, I want an honest unconfirmed outcome with my non-password fields retained, so that I can recover without an automatic duplicate submission.
18. As an applicant, I want verification resend and password recovery available without login, so that I can recover before receiving approval.
19. As a pending applicant, I want correct login credentials to explain that review is pending without signing me in, so that I understand why access is unavailable.
20. As an account holder, I want incorrect credentials to receive the existing generic error, so that application status is not disclosed to someone who cannot authenticate my credentials.
21. As an administrator, I want unverified applications separated into an awaiting-email-verification filter and count, so that they are visible without entering the actionable review queue.
22. As an administrator, I want approval and rejection blocked until email verification, so that a decision is made only for a verified applicant.
23. As an administrator, I want to search by organization name, applicant name, and email, so that I can find a relevant record quickly.
24. As an administrator, I want status filters, counts, and paginated results, so that I can manage the review workload without loading every application.
25. As an administrator, I want application details to show the immutable submitted information, so that later profile edits cannot rewrite what I reviewed.
26. As an administrator, I want recent events owned by the organization, so that I can see its existing activity without sample records or another organization's events.
27. As an administrator, I want to approve a verified pending application, so that its organizer can log in and use available approved-organizer functions.
28. As an administrator, I want rejection to require an applicant-visible reason, so that the applicant understands the decision and the record remains accountable.
29. As a rejected applicant, I want an email explaining the final rejection and its reason, so that I understand the result without needing workspace access.
30. As a rejected applicant, I want the service to explain that this account cannot revise, resubmit, or register again with the same email, so that it does not offer an unavailable retry path.
31. As an approved organizer, I want an approval email directing me to login, so that I can use the password I originally supplied without receiving credentials by email.
32. As an approved organizer, I want the existing verification, consent, credential, and account-status checks preserved, so that organization approval does not bypass account eligibility.
33. As an administrator, I want every decision to retain its actor, timestamp, transition, and applicable reason, so that the history explains how the organization reached its current state.
34. As an administrator, I want a competing or stale decision rejected with a refresh requirement, so that I cannot silently overwrite another administrator's decision.
35. As an administrator, I want to suspend an approved organization with a required reason, so that organizer access can be withdrawn with an explanation.
36. As a suspended organizer, I want the suspension reason emailed to me, so that I understand why I can no longer access the workspace.
37. As an administrator, I want suspension to revoke every organizer session and block new login, so that access does not survive through another browser or stale session.
38. As a suspended organizer, I want password recovery to remain available, so that I can maintain my credentials without regaining suspended privileges.
39. As an attendee, I want an organization's suspension to leave my purchased tickets and event access unchanged, so that suspension does not silently cancel my booking or admission.
40. As an administrator, I want suspension to leave existing events and sales unchanged in this slice, so that cancellation, sales stoppage, and refunds occur only through their own explicit rules and actions.
41. As an administrator, I want to reinstate a suspended organization, so that eligible organizers can regain access through a fresh login.
42. As a reinstated organizer, I want an email explaining fresh login is required, so that I do not expect an invalidated session to work again.
43. As an administrator, I want reinstatement to preserve account disabling, so that it cannot accidentally re-enable a disabled identity.
44. As an administrator, I want a committed decision to remain effective when email fails, so that email availability does not control access policy.
45. As an administrator, I want visible decision-email delivery state and a retry action, so that a failed notification can be retried without repeating the decision.
46. As an organizer, I want retries to send only the current decision, so that a delayed approval email does not incorrectly invite me to log in after suspension.
47. As an administrator, I want superseded notifications preserved alongside decision history, so that skipped deliveries do not erase past decisions.
48. As an administrator, I want CSV export of all records matching the current search and filters, so that export reflects the selected population rather than just one page.
49. As an account holder, I want exports to exclude passwords, tokens, and internal delivery errors, so that administrative reporting does not expose credentials or provider details.
50. As an organizer, I want protected requests to check current approval and resource ownership, so that another organizer cannot act on my resources and revoked access cannot rely on cached state.
51. As an administrator, I want my role to grant only explicitly allowed administrative operations, so that it does not implicitly become an organizer identity.
52. As a user, I want labeled, keyboard-usable application and review controls on mobile and desktop, so that I can complete the workflow in my chosen browser.
53. As a user facing an unavailable service or uncertain decision response, I want truthful feedback and a safe refresh path, so that sample records or automatic mutation retries do not masquerade as success.

## Implementation Decisions

- Extend the existing account registration/lifecycle, organization-profile persistence, current-account authorization, administrator review, email delivery, and frontend authentication integrations. Reuse Better Auth credentials and sessions, PostgreSQL transactions, existing account locks, and the current email transport. Keep the implementation proportionate to the project's scope; no replacement identity system or general workflow engine is needed.
- Create the organizer account at initial application, with a trusted server-assigned `ORGANIZER` role, its own globally unique normalized email, and one pending organization profile. Do not accept client-provided role, account status, approval status, verification, approver, decision dates, or derived identity fields. Existing attendee and administrator accounts retain their identity and role.
- Use public `POST /api/v1/organizer-applications` for submission. Its allowlisted input consists of first and last names, email, password, optional phone number, organization name, organization description, affirmative current-terms acceptance, and terms version. Password confirmation stays in the browser. Return a creation acknowledgement that clearly requires verification and administrator approval; never issue a session or imply immediate login eligibility. Keep attendee registration dedicated to attendees.
- Preserve S01 validation and normalization for personal fields, passwords, email, phone, and consent. Omit an empty optional phone from registration. Apply organization-name limits of 2–150 trimmed characters, description limits of 20–2,000, and rejection/suspension-reason limits of 1–500. Use Unicode code-point counting consistently with existing personal-field validation; trim text boundaries, reject whitespace-only values, and render descriptions and reasons as plain text. Organization names are not unique identifiers. Username and organization type are excluded.
- The organizer registration transaction includes the identity, hashed credential, genuine consent, organization profile, immutable application snapshot, and verification-link state required by the existing verification flow. It must roll back as a unit on persistence failure. Enforce normalized-email uniqueness under concurrent submissions; a duplicate returns the existing conflict semantics and changes no existing account, credential, consent, profile, or application. Apply the existing origin, JSON/body-size, no-store, and rate-limit protections to the new public submission operation.
- Send verification email after commit. Successful persistence followed by delivery failure uses the existing account-created/email-failed distinction and explains that the application is saved. Reuse verification, resend, recovery, and reset operations, including current-password verification, link expiration, single-use behavior, throttling, and generic public resend/recovery responses. Never roll back a saved application because email transport fails. Reset and verification do not approve the organization, re-enable a disabled account, or issue a session.
- Preserve the existing four organization states: `PENDING`, `APPROVED`, `REJECTED`, and `SUSPENDED`. Awaiting email verification is a review classification of an unverified pending application, not a fifth approval state. Verified pending applications form the actionable review queue. Verify eligibility on the server when deciding, including after acquiring the transaction lock.
- Store a separate immutable snapshot of the submitted non-secret personal and organization information, linked to the organizer account and organization profile. Passwords and verification tokens must never be copied into this snapshot. Retain submission time and the original consent reference. Subsequent personal-account edits do not rewrite it. There is no applicant update, withdrawal, correction, or resubmission operation in this slice; organization-profile editing after approval belongs to the later profile slice.
- Add durable decision records linked to the application/profile, with decision identifier, actor, server timestamp, previous state, resulting state, reason where required, and a monotonic version for concurrency checks. Retain prior reasons and decisions when a later decision is made. Reuse the existing audit convention, and commit the authoritative state, history, required audit, notification intent, and session revocation together where applicable. An audit/history/revocation persistence failure must roll back the decision.
- Allowed administrator transitions are pending to approved, pending to rejected, approved to suspended, and suspended to approved. Approval and rejection require verified email; rejection and suspension require reasons. Rejection is terminal for the account and reserves its normalized email. No reject-after-approval, direct pending suspension, reopening rejection, or arbitrary status replacement is permitted. Reinstatement changes organization approval only; it cannot change account status or verification.
- Use administrator-only `GET /api/v1/admin/organizers`, `GET /api/v1/admin/organizers/stats`, `GET /api/v1/admin/organizers/:id`, and `GET /api/v1/admin/organizers/export`. Organizer identifiers refer consistently to organization profiles. The list and export share validated search/status filtering; the list uses bounded pagination and stable ordering. Counts use the same search scope and separate awaiting-verification, verified-pending, approved, rejected, and suspended populations. Details include the immutable application, current status/version, decision history, notification state, and recent events belonging to that profile. Return real empty states when no records/events exist. Keep current personal contact details, where shown, distinguishable from submitted snapshot values.
- Use `PATCH /api/v1/admin/organizers/:id/status` with a target state, the last-read version, and a reason when required. Resolve the administrator from the authenticated session. Return the committed status/version and decision identifier. A stale version or disallowed transition produces a conflict without side effects. For competing decisions, only the first commit against that version succeeds; the other administrator must refresh. Version checks must also reject an old decision after an approve/suspend/reinstate cycle returns the profile to the same state.
- Serialize suspension and login/session creation with the existing per-account lifecycle lock. Every protected organizer request must check current account eligibility and approved organization status; missing organization profiles fail closed. Suspension revokes all existing sessions in its transaction and prevents a concurrent login from leaving a usable session after suspension commits. Reinstatement never revives old sessions. Existing account-check precedence remains in place before the additional organizer check: wrong credentials remain generic, and disabled, unverified, consent, and credential-recovery outcomes retain their established meanings.
- Correct credentials for an otherwise eligible pending, rejected, or suspended organizer return a distinct, non-session status explanation. The frontend must understand these outcomes and avoid treating them as an authenticated workspace. The current-account read and protected operations enforce the same organization eligibility so stale cookies or frontend caches cannot bypass it. Approved organizers use the existing cookie/session lifetime and exact role checks; administrators do not inherit organizer rights. Keep shared account self-service available only through an eligible authenticated session, while verification/resend/recovery retain their unauthenticated flows.
- Suspension changes organizer access only. Do not mutate events, stop their sales, cancel tickets, initiate refunds, or remove attendee admission because of suspension. Later event-management, booking, and admission slices must preserve this boundary unless the product explicitly revisits it. S03 supplies approval eligibility for later event tools but does not implement event creation, publishing, or check-in.
- Record a durable notification intent with each committed approval, rejection, suspension, or reinstatement. Use a small persisted delivery record and the existing transactional email transport; external delivery happens after the database transaction. Approval emails link to ordinary login without credentials or automatic sign-in tokens. Rejection and suspension emails include their recorded reasons. Reinstatement emails explain that fresh login is required. All messages distinguish email verification from organization approval.
- Expose delivery state in administrator details and a version/decision-specific retry operation, `POST /api/v1/admin/organizers/:id/decisions/:decisionId/retry-email`. Retrying never changes approval state, creates another decision, or repeats session revocation. Deduplicate concurrent delivery claims for the same notification. Re-read the current decision before dispatch; an outdated unsent or retried notification is marked superseded and is not sent. Preserve every historical decision and notification result. Once a provider has accepted an email it cannot be recalled; provider acceptance is not proof of inbox receipt, and ambiguous delivery must not be labeled confirmed delivery. Persist enough state to make pending/failed delivery recoverable after a process restart.
- CSV includes every record matching the current search/status filters, with applicant contact information, organization details, current review/approval status, submission/decision dates, and no credentials, tokens, or internal delivery errors. Use the same administrator authentication and current eligibility as review endpoints. Produce correctly escaped CSV and neutralize spreadsheet formula interpretation of applicant-controlled cells. Do not silently truncate an export to the current page or substitute mock data.
- Replace the disabled organizer application preview and associated unavailable copy with the live form, consent, verification guidance, and actual submission outcomes. Replace administrator organizer mocks with the live endpoints and approved terminology. Enable only the S03 business endpoints and controls; avoid mounting unrelated placeholder operations when connecting the administrator router.
- On uncertain application submission, clear password inputs, retain non-password fields in the form, state that creation is unconfirmed, and offer login, verification resend, and password recovery. Do not automatically submit again, expose a public email-based application lookup, or claim a repeat registration reconciles the first attempt. A login link may lead to a non-session pending explanation; it does not promise workspace access.
- On a lost administrator-decision response, do not automatically replay the mutation. Refresh the organization detail/history to establish the committed outcome; if the read fails, retain an unconfirmed message and require refresh before another decision. On a version conflict, show the newly read state and require a deliberate decision against its version. Email failure is a separate outcome from a successfully committed decision.
- Prepare schema changes for snapshot, decision version/history, reasons, and notification state without inventing historical application details or decision actors. Before migration, inspect existing organizer records and relationships on the verified target using aggregate, non-secret output. Preserve established states and account identities; mark absent legacy evidence explicitly rather than manufacturing consent, verification, decisions, or application snapshots. Update controlled organizer test fixtures to include a valid approved organization profile where login is expected.

## Testing Decisions

- Good tests assert observable application behavior: HTTP responses, cookies, persisted state after reload, application visibility, authorization, durable history, captured email content, delivery states, and rendered user outcomes. Avoid helper-call-count tests, private implementation assertions, and component snapshots that merely mirror the code structure. Database reads are appropriate for atomicity, immutable evidence, and session/audit persistence that cannot be fully observed through public reads.
- The user confirmed the primary backend boundary as the existing public HTTP application, using real Express routing, Better Auth, Prisma, and the guarded dedicated PostgreSQL test database with controlled email delivery. Extend the existing application factory's email injection at the external delivery boundary rather than mocking internal registration, decision, or authorization services. Reuse its controllable clock for expiry and retry scenarios. No new service-level test seam is required.
- Existing registration, verification, authorization, session, password-recovery, terms-acceptance, and account-maintenance HTTP integration suites are prior art for transaction rollback, exact credentials, email capture, explicit roles, current account checks, and lifecycle races. Preserve test-database identity checks and test-owned cleanup; never substitute the development database. Update existing organizer authorization fixtures and unavailable-route expectations specifically for the newly implemented S03 endpoints.
- Cover valid application creation, every field boundary, Unicode counting, optional phone, plain-text content, exact password handling, stale/missing terms, unknown/protected fields, normalized-email conflicts across all roles, and two simultaneous submissions. Assert account/profile/snapshot/credential/consent/link atomicity, zero sessions, and no mutation of an existing attendee identity. Inject a persistence failure through the established test mechanism to prove rollback rather than merely asserting a transaction helper was called.
- Cover successful verification, wrong-password verification preserving link usability, expired/consumed links, resend/recovery protections, saved-application/email-failed responses, and pending status after verification/reset. Assert unverified applications are visible only in the separate review classification and cannot be approved or rejected through direct HTTP requests.
- Cover each allowed and forbidden decision transition, required reasons and limits, missing records, stale versions, simultaneous approve/reject requests, and a version from before a suspend/reinstate cycle. Assert one committed winner, unchanged losing state, immutable snapshot/history, actor identity, timestamps, durable audit, notification intent, and rollback when a required write fails.
- Cover login before verification, verified pending login, rejected login, approved login, and suspended login; correct credentials produce the applicable gate without a session where access is barred, while incorrect credentials remain generic. Cover disabled-account precedence, missing consent, credential-recovery gates, missing organization profiles, exact role allowlists, and cross-organizer resource isolation on the S03 surfaces. Exercise approval eligibility through a test-only protected organizer fixture where later business routes do not yet exist; never expose that fixture in the production app.
- Cover suspension revoking multiple browser sessions, a login racing suspension, old sessions remaining invalid after reinstatement, fresh login succeeding only when account eligibility permits, and disabled accounts remaining disabled. Seed owned events, ticket/booking records, and relevant attendee data as needed and assert suspension changes none of their state. Do not claim S04 publishing or later admission flows are implemented from these fixtures.
- Cover search/filter/page consistency, all review classifications, counts, owned-event isolation, empty results, immutable submitted details after current-profile edits, and CSV across more than one page. Assert administrator-only access, correct quoting, formula-safe cells, and exclusion of secrets/internal errors.
- Cover all four decision-email types, required reason content, ordinary login links, no password/token disclosure, provider rejection, pending delivery after restart, concurrent retries, superseded decisions, and retrying without another decision or session mutation. Distinguish captured/provider-accepted delivery from verified inbox receipt. Check the race where a newer decision commits before dispatch and ensure the stale notification is skipped; an already handed-off message cannot be retracted.
- The user also confirmed browser tests through the actual application, administrator review, and login routes. Reuse the existing Chrome/Edge browser harness and controlled HTTP boundary to test validation, consent, verification guidance, email-failure messaging, lost/unusable responses, non-password draft preservation, stale administrator decisions, search/filter/export controls, and current account refresh after suspension. Existing verification and account-switching browser tests and frontend injected-transport authentication tests are prior art. Add transport-level assertions only for exact new payload/error mappings that browser behavior does not already prove.
- Acceptance includes relevant backend HTTP suites, frontend behavior/contract tests, frontend and backend type/build checks, and a localhost browser walkthrough joining the real frontend and backend with controlled test email: apply, verify, approve, log in, suspend, confirm session loss, reinstate, and log in afresh; separately reject another applicant and verify the final denial and reason. Confirm the separate attendee account remains unchanged. Report blocked/unrun checks and real-delivery limitations explicitly. Controlled email is not proof of delivery to real applicants.

## Out of Scope

- Attendee promotion, shared identities, role switching, normalized-email reuse, multiple organizations per account, shared staff accounts, team invitations, username, and organization type.
- Authenticated pending/rejected application workspaces; applicant correction, withdrawal, resubmission, appeals, reopening rejection, or automatic cleanup that releases a rejected account's email.
- Organization-profile editing after approval, payout destinations, financial onboarding, document/KYC uploads, a new personal-profile feature, or arbitrary account administration through S03.
- Event creation, editing, publishing, check-in, cancellation, sales stoppage, refunds, and attendee admission changes. S03's approval authorization must not be used to silently add event-side suspension effects.
- In-app administrator notifications, general notification preferences, bulk decisions, scheduled reminders, and a general-purpose messaging/queue platform.
- A replacement authentication, credential, session, verification, recovery, or terms system; automatic login from application or decision emails; administrator inheritance of organizer privileges.
- Application implementation, database mutation/migration execution, deployment, live-account changes, or real applicant emails during this specification task. The ready-for-agent label describes specification readiness and does not itself start implementation or waive existing activation gates.
