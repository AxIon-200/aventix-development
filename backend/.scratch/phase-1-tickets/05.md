## Acceptance criteria

- [ ] Provide the approved dedicated acceptance operation requiring normalized email, current password, ACTIVE status, verified email, true acceptance, and the current terms version.
- [ ] Record genuine acceptance with a server timestamp; return 200 without issuing a session. The user logs in separately afterward.
- [ ] Missing consent blocks login and protected access through existing sessions. TERMS_ACCEPTANCE_REQUIRED uses 403 and is disclosed only after correct credentials, preserving prior status/verification gates.
- [ ] Unverified users must verify first, disabled users cannot complete acceptance, and logout/recovery retain their separately approved availability.
- [ ] Do not fabricate consent or verification for existing accounts and do not require acceptance of future revisions as part of this phase.
- [ ] Apply agreed response, credential-throttling, origin/CSRF, and bypass controls. HTTP tests cover genuine completion, invalid credentials, outdated/missing acceptance, gate enforcement, and successful subsequent login.
