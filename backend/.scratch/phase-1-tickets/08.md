## What to build

Let eligible signed-in users replace their password by proving the current password, removing other access while continuing in the requesting browser.

This ticket implements only its slice of parent #33's approved specification. Use HTTP integration tests with real Better Auth/Prisma, the verified isolated test database, and controlled email delivery. Include the relevant persistence, safe response/error contracts, policy enforcement on native routes, and focused tests; no frontend work is required. Retain the school-project scope. Publishing or labeling this ticket does not authorize implementation: ticket 1's prerequisites and explicit separate implementation approval remain mandatory.

## Acceptance criteria

- [ ] Require an eligible authenticated session, current password, and valid new password; reject the current password as the new value.
- [ ] Incorrect current passwords and invalid new passwords leave credentials and sessions unchanged; do not trim or normalize passwords.
- [ ] Successful change returns 200, invalidates every other session and all outstanding reset links, and preserves authenticated access in the requesting session.
- [ ] Client options cannot override required revocations; direct provider password routes cannot bypass the same rules.
- [ ] Persist a successful-change audit without passwords or raw tokens and apply agreed origin/CSRF, IP, and safe error controls.
- [ ] Use HTTP tests with multiple sessions and outstanding reset links to verify revocation, retained current access, credential validation, direct-route protection, and secret-safe results.
